# AI Security Assistant

## Purpose

The CyberShield AI assistant exists to help a business owner understand a verified finding in plain language and decide what to do next. It can explain the issue, why it matters, how to remediate it, and how to verify the fix. It is not a detector, a scanner, a risk engine, or an automatic remediation engine.

## Data flow

Finding -> authorization -> evidence -> sanitization -> context -> provider -> validation -> response

The backend loads the actual finding from the database, confirms the authenticated user owns it, and builds the AI context from the stored finding metadata and verified evidence. The assistant receives only the necessary data required to explain the issue and propose safe next steps.

## Trust boundary

CyberShield keeps a strict separation between trusted and untrusted data. Trusted data includes the scanner findings, the recommendation metadata, the business/website relationship, and the current user context. Untrusted target content is never treated as an instruction. Website content never overrides the application or developer instructions.

## Grounding

The AI assistant cannot create or modify scanner truth. It cannot invent vulnerabilities, CVEs, versions, headers, cookies, ports, IP addresses, or evidence. It cannot claim that a finding has been fixed without a fresh verification check. The risk score, severity, and evidence remain parts of the deterministic CyberShield engine and are never re-generated by the AI.

## Security

Before any AI request is sent to an external provider, CyberShield redacts sensitive fields such as passwords, JWTs, cookies, authorization headers, API keys, and other credentials. The redaction layer is reused by the AI context builder so prompts do not leak secrets or environment values.

The AI service validates structured output before it is returned to the user. Unsupported claims such as invented CVEs, false remediation success, or invented evidence are rejected and replaced with deterministic fallback guidance when appropriate.

## Failure handling

If the configured provider is unavailable, times out, rate-limits the request, returns malformed JSON, or fails unexpectedly, the application falls back to deterministic guidance based on the stored finding and recommendation metadata. This fallback is clearly labeled and it never pretends to be true AI analysis.

## Limitations

AI guidance may be incomplete or missing context if a finding lacks strong evidence. The user should validate the recommendation against the current site configuration and the most recent scan result before treating the fix as complete. CyberShield AI is an assistant; it is not an autonomous security control.

## Day 18 quality and security controls

- Finding titles, descriptions, evidence, recommendations, and website metadata are untrusted data. They are never treated as instructions.
- Trusted instructions explicitly prohibit prompt disclosure, secret disclosure, invented scanner facts, and unsupported remediation or verification claims.
- AI output is required to use the structured response shape and verified-evidence entries must be grounded in backend evidence.
- Responses containing prompt-override attempts, prompt/secret disclosure requests, invented CVE/CVSS claims, or unsupported completion claims are rejected.
- Synthetic secret patterns are redacted before context is sent to a provider, including authorization headers, cookies, passwords, API keys, secrets, and JWT-like values.
- Provider failures and malformed output use deterministic, clearly labeled fallback guidance.
- Owner-scoped finding retrieval remains the authorization boundary for every AI request; AI cannot change finding status, severity, risk, ownership, remediation, or verification state.
